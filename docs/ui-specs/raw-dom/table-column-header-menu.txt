*** TWO STRUCTURAL CORRECTIONS TO THE DESIGN DOC ***

CORRECTION A — sub-panels are FLYOUTS, not push/pop panels.
  Clicking "Change type" opened a SECOND panel to the RIGHT of the menu
  (x≈877..1077, top-aligned near the viewport top), and THE PARENT MENU STAYED
  FULLY VISIBLE AND OPEN beside it. There is no back arrow, because there is
  nothing to go back from — both panels are on screen at once.

  The design doc specifies:
     "MenuList — ... push/pop sub-panels with a back arrow"
     "Esc — Pop one sub-panel; at the root, close"
  That is the WRONG MODEL for this surface. Notion uses an adjacent flyout, the
  way a classic nested menu does.

  NOTE the inconsistency: TemplateManager/AutomationManager in OUR code already
  use push/pop-with-back-arrow, and the create-database modal is a full overlay.
  Notion itself may use push/pop elsewhere — the settings sidebar's sub-panels
  are not yet captured. DO NOT generalise from this one observation the way
  FINDING 3 was over-generalised earlier. Capture the sidebar sub-panels before
  deciding whether MenuList needs flyout mode, push/pop mode, or both.

CORRECTION B — the type list is SINGLE-COLUMN here.
  The "+ Add property" type picker is a TWO-column grid (property-type-picker.txt).
  This "Change type" list of the same types is ONE column.
  So the layout is a property of the SURFACE, not of the data. MenuList needs the
  column count as a per-panel option.
