*** TWO STRUCTURAL CORRECTIONS TO THE DESIGN DOC ***

CORRECTION A — sub-panels are FLYOUTS, not push/pop panels.
  Clicking "Change type" opened a SECOND panel to the RIGHT of the menu
  (x≈877..1077, top-aligned near the viewport top), and THE PARENT MENU STAYED
  FULLY VISIBLE AND OPEN beside it. There is no back arrow, because there is
  nothing to go back from — both panels are on screen at once.

  The design doc specifies:
     "MenuList — ... push/pop sub-panels with a back arrow"
     "Esc — Pop one sub-panel; at the root, close"
  That is the WRONG MODEL for this surface. Notion uses an adjacent flyout, the
  way a classic nested menu does.

  NOTE the inconsistency: TemplateManager/AutomationManager in OUR code already
  use push/pop-with-back-arrow, and the create-database modal is a full overlay.
  Notion itself may use push/pop elsewhere — the settings sidebar's sub-panels
  are not yet captured. DO NOT generalise from this one observation the way
  FINDING 3 was over-generalised earlier. Capture the sidebar sub-panels before
  deciding whether MenuList needs flyout mode, push/pop mode, or both.

CORRECTION B — the type list is SINGLE-COLUMN here.
  The "+ Add property" type picker is a TWO-column grid (property-type-picker.txt).
  This "Change type" list of the same types is ONE column.
  So the layout is a property of the SURFACE, not of the data. MenuList needs the
  column count as a per-panel option.

*** THREE MORE CORRECTIONS TO THE DESIGN DOC ***

CORRECTION C — menus nest at least THREE levels.
  Calculate (L1 menu) → Count (L2 flyout) → the count functions (L3 flyout).
  The design doc's MenuList models one level of sub-panel. It needs arbitrary
  depth, and each level needs its own independent flip/shift decision.

CORRECTION D — a menu row can be a TOGGLE, and can carry a DESCRIPTION.
  "Show large counts as 99+" is a switch with a two-line explanatory caption
  underneath, sitting inside a menu above a divider.
  MenuRow in the design doc has: id, icon, label, hint, value, checked, danger,
  disabled, disabledReason, submenu, onSelect.
  It needs at minimum: `description` (caption under the label) and a control
  kind (`row` | `toggle`). Combined with the `badge` field already found in the
  type picker, MenuRow is meaningfully wider than designed.

CORRECTION E — calculations are NOT only a footer-row feature.
  The plan puts "Calculations row" in M11 as its own surface. The same function
  set is reachable here in the column header menu, at M1. Either M1 ships the
  Calculate sub-panel (and M11 only adds the footer presentation), or M1 ships a
  header menu with one row that does nothing. Sequencing decision for the plan.

FUNCTION SET so far: Count all / Count values / Count unique values / Count empty /
Count not empty, plus a Percent branch (not yet captured) and None.
Our backend's aggregations (services/db/query/aggregations.py) include count,
count_values, unique, empty, not_empty, percent_empty, percent_checked, sum,
average, median, min, max, range, earliest_date, latest_date, date_range,
checked, unchecked — so the engine already covers these. Only the UI is missing.
NOTE: this was captured on a TEXT property; numeric/date properties will offer
more branches (Sum, Average, …). Re-capture on the Number and Date columns.
