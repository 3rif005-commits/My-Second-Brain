*** THE PEEK IS URL-ADDRESSABLE — AND ENCODES ITS MODE ***
  Opening the peek changed the URL to:
      ...?v=<viewId>&p=<pageId>&pm=s
  - `v`  = the view
  - `p`  = the peeked page (row)
  - `pm` = peek mode; `s` for side peek
  So the peek is deep-linkable AND the mode is part of the address. Reloading
  restores it; sharing the link opens the same row in the same mode.

  Our RowPeek is component state only (`peekRowId` in TableView.tsx:180) — not in
  the URL, not restorable, not shareable. The design doc already calls for
  "URL-addressable via a search param"; this confirms the exact shape to copy,
  including the mode parameter. Suggest `?p=<noteId>&pm=s|c` to match.

  *** ORDERING IS ALPHABETICAL, NOT TABLE ORDER ***
    Peek order:  Checkbox, Date, Files, Multi-select, Number, Person, Select,
                 Status, Text, URL
    Table order: Name, Text, Number, Select, Multi-select, Status, Date, Person,
                 Checkbox, URL, Files

    But the "Property visibility" sidebar panel lists them in TABLE order.
    So Notion uses BOTH orderings deliberately:
      - Property visibility panel → table order (you are reordering the table)
      - Peek / Group / Sort pickers → alphabetical (you are finding a property)
    Our RowPeek sorts by `position` (RowPeek.tsx:69-72), i.e. table order.
    This is a real, checkable difference.

  - Empty values render the literal muted word **"Empty"**, not a blank cell.
    Ours renders whatever the cell component renders for null.
  - The title property is NOT in this list (it is the heading instead).
  - "+ Add a property" is the last row — inline property creation from inside the
    peek. Ours has no such affordance.

================= "+ Add a property" INSIDE THE PEEK =================
Opens the type picker — but rendered DIFFERENTLY from the table header's version.

| | Table header `+ Add property` | Peek `+ Add a property` |
|---|---|---|
| Name placeholder | `Type property name…` | **`Property name`** |
| Section label | `Select type` | **`Type`** |
| Type layout | **TWO-column grid** | **SINGLE-column list** |
| Search icon on section header | yes | yes |
| AI Autofill section | yes | yes |

  Same conceptual picker, three cosmetic differences, two hosts. This is more
  evidence for host-parameterised panels — but also a caution: Notion is not
  perfectly self-consistent, so we should pick ONE set of copy and one layout
  rule rather than reproducing both. RECOMMEND: single-column in narrow hosts
  (peek, sidebar), two-column in wide ones (the header popover), one shared
  copy string.
