*** CORRECTIONS TO THE PLANNED SPEC ***
1. The property NAME field is NOT inside the popover. Clicking "+ Add property"
   turns the header cell into an inline input, placeholder "Type property name…",
   AUTOFOCUSED (verified: document.activeElement is that input). The popover hangs
   below it. Our §2 draft assumed name+type both inside one popover.
2. To the left of that input is an ICON button (emoji) — a property can have its
   own icon. We have no such concept.
3. The type list is a **TWO-COLUMN GRID**, not a single-column list. This changes
   the MenuList primitive: it needs an optional grid mode, and ←/→ arrow handling,
   not just ↑/↓.
4. "AI Autofill" is its own section ABOVE "Select type", with two rows carrying a
   plan-tier badge ("Basic") and a chevron indicating a sub-panel.
5. The "Select type" SECTION HEADER carries its own search icon — search is
   attached to the section, not to the popover as a whole.

FINDING 1 — the name field is NOT the type filter.
  Typed "sel" into the autofocused property-name input. The type grid did NOT
  filter: Text / Number / Select / Multi-select / Status / Date / Person /
  Files & media all still shown, unchanged and unreordered.
  The name input names the property. That is all it does.
  → This invalidates the planned checklist shot 12 ("type `sel` into its search
    field"), which assumed one combined field. Two separate inputs exist.

FINDING 2 — type search is a separate, INITIALLY HIDDEN input.
  The "Select type" section header carries a magnifier icon at its right.
  Clicking it EXPANDS a full-width text input directly beneath the section
  header, inside the popover, and focuses it. The section header stays visible
  above the input.

FINDING 3 — filtering changes the LAYOUT, not just the contents.
  Query "rel" produced:

    AI Autofill                    ← section unchanged, NOT filtered
      Summarize   Basic   >
      Translate   Basic   >
    Select type          [search input: "rel"]
      ↗ Relation                   ← SINGLE COLUMN, not the 2-col grid
      ────────────────             ← divider
      [G] Google Drive File  ⬆     ← integration group, blue upgrade badge

  So: the grid is 2 columns when unfiltered and 1 column when filtered.
  A MenuList grid mode must handle that transition, and the arrow-key model has
  to change with it (←/→ meaningful in grid mode, meaningless in list mode).

FINDING 4 — the "AI Autofill" section is exempt from the type search.
  It stays fully rendered while the type list is filtered down to one match.
  So search scope is per-section, matching the search icon living on the
  "Select type" header rather than on the popover.

FINDING 5 — third-party types are grouped and badged.
  "Google Drive File" appears below a divider with a blue upward-arrow badge,
  i.e. an upgrade/connect affordance rather than a plain selectable row. The
  four integration types are out of scope for us, but the BADGE + DIVIDER
  pattern is reusable for our own "requires setup" rows.

KEYBOARD — Escape (real key events)
  Escape CANCELS the new-property popover and discards the typed name: after two
  presses the header row was back to just "Name" + "Add property", with no
  property created and no "sel" left behind.
  CONTRAST: the create-database data-source picker IGNORES Escape entirely
  (see create-database-picker.txt). So Notion is NOT internally consistent here —
  a popover cancels on Escape, that full-screen modal does not.
  For our build: adopt Escape-cancels everywhere. It is the majority behaviour,
  it matches our existing ConfirmDialog/PromptDialog convention, and the modal's
  non-dismissal reads as a bug rather than a decision.
