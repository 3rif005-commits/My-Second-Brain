*** MAJOR SCOPE FINDING — Notion groups by ANY property type ***
  The list offers Name (title), Checkbox, Date, Multi-select, Number, Person,
  Select, Status, Text, URL.

  Our `GROUPABLE_PROPERTY_TYPES` (lib/database/types.ts:134) is:
      ["select", "status", "multi_select"]
  — three types. Notion offers at least ten, including Text, Number, Date,
  Checkbox, Person and URL.

  This is a genuine M6 scope decision, and it is NOT purely frontend: the
  backend's `services/db/query/grouping.py` GroupBySpec would have to group by
  ranges/buckets for Number and Date, and by boolean for Checkbox. That is real
  engine work, not a UI change.
  → FLAG TO THE USER. Do not silently widen M6. Options: (a) ship the 3 types we
    support and show the rest disabled with a reason, (b) add engine support for
    the scalar types first as a backend sub-task, (c) mirror Notion's list and
    accept that some choices 400.
  Recommendation: (a) for M6 — a disabled row with a reason is honest and keeps
  M6 frontend-only; (b) as a separate, later, backend-scoped task.

  ORDERING: the list is ALPHABETICAL by property name (Name first as the title,
  then Checkbox, Date, Multi-select, Number, Person, Select, Status, Text, URL),
  NOT in table/position order. Our pickers use position order everywhere.

NOTES / DIFFERENCES BETWEEN THE TWO PANELS
- Title differs by state: "Group by" (a setting with a current value) vs
  "New sort" (an additive action — sorts are a LIST, groups are singular).
- Search placeholder differs: "Search for a property…" vs "Sort by…".
  Placeholders are per-panel copy, not one shared string.
- Group has a "None ✓" row; Sort has none, because there is no sort yet and the
  panel is titled "New sort" rather than "Sort".
- **"Files" appears in Sort but NOT in Group.** Per-type capability differs per
  panel, and the UI filters the property list accordingly. So each panel needs
  its own "is this property eligible" predicate — a single shared
  `isGroupable`/`isSortable` pair, not one "supported types" list.
- Both lists are alphabetical.

THE BAR
  Applying a sort adds a chip to the same bar the filter uses, placed BEFORE the
  filter chip:
      [↑ Name ▾]   [⧩ 1 rule ▾]   [+ Filter]        ← one sort
      [⇅ 2 sorts ▾] [⧩ 1 rule ▾]  [+ Filter]        ← two sorts
  - ONE sort  → chip shows a direction arrow + the PROPERTY NAME ("↑ Name").
  - TWO sorts → chip collapses to a COUNT ("⇅ 2 sorts"), like the filter's
    "1 rule". So the chip label is singular-specific and plural-generic.

THE EDITOR (popover anchored under the chip)
--- verbatim, two sorts ---
⠿  [Aa Name   ▾]  [Sort A → Z      ▾]  [×]
⠿  [#  Number ▾]  [Sort low → high ▾]  [×]
+  Add sort
🗑  Delete sort
--- end ---

ROW ANATOMY
  [drag handle ⠿] [property ▾] [direction ▾] [× remove this sort]
  - Each row is individually removable via its own ×.
  - "Delete sort" at the bottom removes ALL sorts (distinct from the per-row ×).
  - Rows are drag-reorderable — sort PRECEDENCE is the row order.

*** DIRECTION LABELS ARE TYPE-AWARE — now proven with two data points ***
      Text / Title  →  "Sort A → Z"      / "Sort Z → A"
      Number        →  "Sort low → high" / "Sort high → low"
  Date presumably "Sort earliest → latest"; NOT captured.
  Our backend's SortSpec is {property, direction: "asc"|"desc"} — the wire format
  needs no change. This is a LABEL concern only: render the label from the
  property type, never a generic "Ascending/Descending".

"ADD SORT" PROPERTY PICKER
  - Autofocused "Search for a property…"
  - **Already-sorted properties are EXCLUDED.** "Name" was absent from the list
    once it was sorted. So the picker is filtered against the current sort list.
  - "Status" rendered GREYED. Cause not established — possibly because the Status
    property has no options configured. OBSERVED, NOT EXPLAINED; re-test with
    options present before the spec claims a rule.

*** "No Select" — the automatic empty group ***
  Rows with no value for the grouped property fall into a group named
  **"No <PropertyName>"** — here "No Select". It appears in the Groups list like
  any other group, and here it is HIDDEN (greyed, eye-with-slash) because
  "Hide empty groups" is on.
  Our backend's grouping produces groups from values; the "no value" bucket's
  NAMING CONVENTION ("No Select") is a UI concern and must be specified.

THE GROUPED TABLE
