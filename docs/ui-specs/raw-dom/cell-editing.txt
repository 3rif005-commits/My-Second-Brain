================= CELL INTERACTION IS TWO-STAGE =================
  1st click  → SELECTS the cell. A blue border appears, plus a small circle at
               the cell's bottom-right corner. NO editor opens.
  2nd click  → OPENS the editor in place.
  Enter on a selected cell did NOT open the editor in this test (pressed once
  after the first click, nothing happened) — TBD whether Enter opens editors for
  other types, or whether a second click is the only route.

  → This two-stage model is a real difference. Our cells (cells/SelectCell.tsx
    etc.) open their editor on the FIRST click. Notion's first click is a
    spreadsheet-style selection.
  → The corner circle is the same unexplained affordance noted in
    row-affordances-and-menu.txt. Still TBD; it appears on cell SELECTION.

================= THE SELECT EDITOR =================
Opens IN PLACE — the cell itself becomes a search input; a panel hangs below it.

STATE: no options exist yet
--- verbatim ---
[ Search for an option…  ]        ← the cell becomes this input, autofocused
Select an option or create one    ← EMPTY-STATE copy, muted
--- end ---

STATE: after typing "Alpha"
--- verbatim ---
[ Alpha ]
Select an option or create one
Create  [Alpha]                   ← "Alpha" rendered as a COLOURED CHIP PREVIEW
--- end ---

  *** The create row PREVIEWS the chip with its auto-assigned colour. ***
  You see what the option will look like before committing. Notion assigns the
  colour itself; the user does not pick it at creation time.
  Our RelationPicker/SelectCell have no create-on-type at all — a select option
  can only be added by editing the property.

STATE: after Enter
  The option is created, applied to the cell, and rendered as a chip in the cell.
  One keystroke does: create option + assign value + close editor.

--- structure, top to bottom ---
[ Aug 31, 2026 ]  [ Aug 31, 2026 ]        ← TWO date inputs: start | end

ELEMENTS
  - TWO text inputs when End date is on, ONE when off. The second appears/
    disappears with the toggle.
  - "Today" is a text shortcut in the calendar header, not a row.
  - Two TOGGLES (End date, Include time) and two VALUE+CHEVRON rows
    (Date format, Remind) in one panel — the same MenuRow kinds already
    established.
  - "Clear" is a plain row above the help link, not a danger-styled one.
  - A "? Learn about …" help link appears here AND in the Group panel. It is a
    recurring footer idiom.

MAPS TO OUR DateValue (lib/database/types.ts:285)
  Our DateValue models start/end/time — the wire format is adequate.
  "Date format" and "Remind" are new config we do not model. Date format is
  presentation (per-property, schema-level); Remind is a notification feature
  we have no equivalent for — OUT OF SCOPE, note and skip.

FIXTURE AUDIT AND FIX (2026-08-31)
  Four properties had been created with the WRONG TYPE during the fixture build,
  because a batched click landed on the unfiltered type grid when the type-search
  input had collapsed (see property-type-picker.txt, FINDING 2 — the expansion
  does not persist).

  Audited by zooming on the header row and reading the TYPE ICONS — the DOM does
  not expose property type as text, and the header's only <svg> is the drag handle.

  | Property  | Was      | Now      |
  |-----------|----------|----------|
  | Status    | Select   | Status   |
  | Person    | Status   | Person   |
  | Checkbox  | Person   | Checkbox |
  | URL       | Person   | URL      |
  | Date      | Select   | Date     | (fixed earlier)
  All others (Name, Text, Number, Select, Multi-select, Files) were already correct.

  METHOD NOTE: to read a property's true type, either zoom on the header row and
  read the icon, or open the header menu → "Change type" and read the ✓. The
  latter is authoritative. Property type is NOT recoverable from innerText.

  BONUS FINDING while fixing: a STATUS property's header menu has an extra row
  the others lack — **"Display as    Select  >"** — letting a status render as a
  plain select. Another type-conditional row, on top of "Edit property".

THE STATUS CELL EDITOR
================================================================
Opened by clicking the cell THREE times in this run (select, then open). The
two-stage model holds but the second click did not always register — TBD whether

--- verbatim ---
[ Search for an option ]          ← note: NO ellipsis, unlike Select's
                                    "Search for an option…". Copy differs per type.
To-do                             ← GROUP HEADER
  ● Not started                   ← grey dot
  ── divider ──
In progress                       ← GROUP HEADER
  ● In progress                   ← blue dot
  ── divider ──
Complete                          ← GROUP HEADER
  ● Done                          ← green dot
  ── divider ──
⚙  Edit property                  ← A ROW INSIDE THE CELL EDITOR
--- end ---

*** FOUR DIFFERENCES FROM THE SELECT EDITOR ***
  1. Options are GROUPED under the three status groups (To-do / In progress /
     Complete), each with a group header and a divider. Select has no grouping.
  2. NO CREATE-ON-TYPE. Select offers "Create [x]"; Status does not — status
     options are managed on the property, not invented from a cell.
  3. Options render as a COLOURED DOT + label, not as a filled chip.
  4. There is an **"Edit property"** row at the BOTTOM of the editor, linking
     from the cell straight to the property config. Select's editor has none.

  This is exactly why the spec refused to write Status from the Select pattern.
  Three of these four would have been wrong.

  Our StatusCell (cells/StatusCell.tsx) renders a flat list with no groups. Our
  backend DOES model status groups (GroupBySpec's `mode: "option" | "group"`,
  and DatabaseShell.tsx:180 defaults to "option"), so the data is there.
